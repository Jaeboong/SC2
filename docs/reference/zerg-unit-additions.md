# 저그 캠페인 유닛 추가/교체 검토 (Zerg Campaign Unit Additions)

> 설계 문서(design spec)입니다. 구현이 아니며 코드/맵/빌더를 수정하지 않습니다.
> **범위**: 저그는 팩션 선택제가 아니다. 표준 Zerg 종족 전체에 **전역(global)**으로,
> 캠페인/협동전 유닛 몇 개를 추가하거나 기본 유닛과 교체하는 것만 다룬다
> (테란의 "메딕 + 골리앗 추가" 아이디어와 동일한 성격). 모든 Zerg 플레이어가 동일하게 얻는다.
> 지상 전투 중심(프로젝트는 AI 전투 공중 유닛을 기본 차단).

## 0. 메커니즘 요약 (전역 데이터 편집)

- 이것은 **전역 데이터 편집**이다: 유닛 데이터 + 해당 종족의 생산(부화장 테크에서 train 또는 morph) 항목을
  Zerg 종족 전체에 추가/수정한다. **플레이어별 트리거/업그레이드는 필요 없다.**
- 핵심 구분:
  - **REPLACE(기본 유닛 교체)**: AI가 이미 "그 기본 유닛을 뽑아라"라고 명령하므로,
    유닛 항목을 캠페인 몸체로 바꾸면 **스톡 AI가 자동으로 그것을 생산**한다. AI 관점에서 가장 매끄럽다.
  - **ADD(신규 옵션 추가)**: 스톡 AI는 표준 빌드에 없는 신규 유닛을 **스스로 선택해 뽑지 않는다.**
    실제로 쓰이게 하려면 프로젝트의 빌드 테이블(빌더의 허용/선호 유닛,
    `sc2team/*` 빌드 정의, `strategy_controller` 생산자 매핑)에 배선해야 한다.
- 저그 전용 함정: **유충(larva) 경제**와 **변태(morph) 기반 유닛**. 아래 각 항목과 §3 참고.

## 1. 이미 표준 멀티(멜리)에 있는 것 — 중복 추가 금지

먼저 착오 방지를 위해, "추가하고 싶을 수 있으나 이미 멜리에 존재"하는 것들:

| 유닛 | 멜리 ID | 비고 |
| --- | --- | --- |
| 러커 (Lurker) | `LurkerMP` | 이미 멜리 유닛. 캠페인 **가시지옥(Impaler)**은 사거리/외형 차이뿐 → 신규 가치 낮음(§2 참고). |
| 무리 숙주 (Swarm Host) | `SwarmHostMP` | 이미 멜리 유닛. 추가 불필요. |
| 살모사 (Viper) | `Viper` | 이미 멜리 유닛(+시전/공중형이라 AI 활용도 낮음). |
| 파멸충 (Ravager) | `Ravager` | 이미 멜리(로치 변태). |
| 맹독충/저글링/로치/히드라/울트라 | 표준 | 모두 멜리 기본. |

프로젝트 빌드도 이들을 이미 사용한다: `ling_bane`, `roach_ravager`, `roach_hydra`, `hydra_lurker`, `ultra_ling_bane`.

## 2. 추천 큐레이션 (전역 추가/교체 후보 ~4–7개)

### 추천도 ★ (권장)

#### 2.1 변종 (Aberration) — **ADD**
- **한/영**: 변종 / Aberration
- **성격**: 느리지만 매우 튼튼한 **중장 근접 몸체**. 능력 없음(패시브 방어).
- **추가/교체**: **ADD**(신규). 로치 교체(REPLACE)는 로치가 파멸충 변태 원천이라 위험 → 신규가 안전.
- **생산 구조/테크**: 부화장 테크상의 중간 건물(예: 로치 소굴/감염 구덩이 계열)에서 유충 변태로 train.
- **왜 좋은가**: 로치와 울트라 사이의 "탱커 브루저" 공백을 메우는, 순수 전투 몸체. 캠페인 상징성 있음.
- **실현성**:
  - (a) 데이터: **캠페인/협동전 의존성 필요**(멜리에 없음).
  - (b) 스톡 AI 사용: 능력 없는 지상 근접 몸체 → **PORT 가능**. 단 ADD이므로 프로젝트 빌드 테이블에
    배선해야 실제로 뽑음. 배선하면 잘 씀.
  - (c) 회귀 위험: 중(의존성 추가 자체가 시작 유닛/카탈로그 위험).

#### 2.2 토라스크 (Torrasque) — **REPLACE 울트라리스크**
- **한/영**: 토라스크 / Torrasque
- **성격**: 죽으면 잠시 후 **부활**하는 대형 근접. 몸싸움 운용은 울트라와 동일.
- **추가/교체**: **REPLACE**(울트라리스크 `Ultralisk` 항목 교체). 또는 별도 ADD 대안.
- **생산 구조/테크**: 울트라리스크 동굴(`UltraliskCavern`) 그대로.
- **왜 좋은가**: REPLACE라서 **AI가 울트라를 뽑을 때 자동으로 토라스크 생산** → 가장 매끄럽다.
  대형 유닛의 임팩트/상징성 강화.
- **실현성**:
  - (a) 데이터: 캠페인/협동전 의존성 필요.
  - (b) 스톡 AI 사용: **자동 사용(REPLACE)** → 최상.
  - (c) 회귀 위험: 중~상. **부활이 보급/유닛수 상한(600) 회계에 미치는 영향**을 반드시 검증
    (무한 재생성/보급 폭주 방지). 데이터 의존성 위험도 있음.

#### 2.3 감염된 테란 (Infested Terran) — **ADD**
- **한/영**: 감염된 테란 / Infested Terran
- **성격**: SC1/캠페인 향수의 아이콘. 캠페인판은 **원거리 사수 보병 몸체**(SC1은 자폭이었음).
- **추가/교체**: **ADD**(신규 원거리 옵션).
- **생산 구조/테크**: 감염 구덩이(`InfestationPit`) 계열에서 train. (표준 감염충의 임시 소환과 별개의 상시 유닛으로.)
- **왜 좋은가**: 강한 향수 + 저그에 부족한 "저렴한 원거리 보병" 결. 시전 능력 없어 AI 친화.
- **실현성**:
  - (a) 데이터: 캠페인/협동전 의존성 필요. **주의**: 원본은 수명 있는 소환 유닛 → 상시 몸체로 쓰려면
    수명/소멸 속성 제거 데이터 필요.
  - (b) 스톡 AI 사용: 원거리 몸체 → PORT 가능하나 ADD이므로 빌드 배선 필요.
  - (c) 회귀 위험: 중(수명 속성 편집 + 의존성).

### 추천도 ☆ (조건부/선택)

#### 2.4 랩터 저글링 (Raptor Zergling) — **업그레이드 방식 권장** (유닛 교체 아님)
- **한/영**: 랩터 저글링 / Raptor Zergling
- **성격**: 절벽 점프 + 추가 피해의 강화 저글링(캠페인 진화 계통).
- **추가/교체**: **REPLACE는 위험** — 저글링은 **맹독충 변태 원천**이라 몸체를 통째로 바꾸면
  `ling_bane`/`ultra_ling_bane` 빌드의 맹독충 변태가 깨질 수 있다. **저글링 강화 업그레이드**
  (대사 촉진 유형)로 스탯/외형만 올리는 편이 안전.
- **생산 구조/테크**: 산란못(`SpawningPool`) 업그레이드.
- **왜 좋은가**: 저글링 정체성 강화, 저위험. 단 임팩트는 크지 않음.
- **실현성**: (a) 캠페인 의존성. (b) 업그레이드형이면 AI가 저글링을 계속 뽑으므로 자동 적용.
  (c) 위험 낮음(변태 체인 보존).

#### 2.5 티라노조르 (Tyrannozor) — 토라스크와 **택일**
- **한/영**: 티라노조르 / Tyrannozor (원시 저그 대형)
- **성격**: 대형 근접 몸체(광역 포효 능력 있으나 핵심은 몸싸움).
- **추가/교체**: 대형 역할이 토라스크와 겹침 → **둘 중 하나만** 채택 권장.
- **실현성**: (a) 협동전(데하카) 의존성. (b) REPLACE면 자동 사용. (c) 토라스크와 유사, 원시 데이터 의존.

### 추천도 ✗ (비권장 / 중복)

- **가시지옥 (Impaler)**: 러커가 **이미 멜리(`LurkerMP`)**에 있고 AI가 자동 잠복 사용.
  캠페인 임페일러는 수동 잠복 마이크로 의존이 커 AI가 제대로 못 씀 → **비권장(중복+미사용)**.
- **스웜링 (Swarmling)**: 저글링과 역할 중복, 임팩트 낮음 → 굳이 필요 없음.

## 3. 저그 전용 함정 (전역 편집 시 반드시 반영)

1. **변태 원천 유닛을 통째로 교체하지 말 것.** 저글링→맹독충, 로치→파멸충, 히드라→러커는
   변태로 만들어진다. 이 원천 유닛(저글링/로치/히드라)을 **REPLACE**하면 변태 능력이 없는 몸체로 바뀌어
   해당 빌드가 깨질 수 있다. → 원천 유닛은 **ADD 또는 업그레이드**로만 다루고, REPLACE는
   **비변태 유닛(울트라 등)에만** 적용.
2. **유충(larva) 경제.** 신규 유닛은 다른 유닛처럼 **유충을 소비**하고 **올바른 부화장 테크 건물**에서
   나와야 AI 생산·보급 회계가 어긋나지 않는다. 임의 소환/무료 생성 경로를 넣지 말 것.
3. **부활/분열 유닛의 회계.** 토라스크(부활) 등은 추가 몸체를 만들어 **800 보급/유닛수 상한**과
   상호작용한다. 재생성 루프·보급 폭주가 없는지 엔진 검증.
4. **ADD는 반드시 배선.** 스톡 AI는 신규 유닛을 스스로 안 뽑는다. ADD 유닛은 빌더의 허용/선호 유닛 표,
   `sc2team` 빌드 정의, `strategy_controller` 생산자 매핑에 함께 넣어야 실제로 등장한다.
   (REPLACE는 이 배선이 필요 없음 — AI가 기본 유닛을 뽑으면 자동 반영.)

## 4. 데이터 의존성 & 회귀 위험

- **모든 기본/폴백 유닛**: 멜리에 이미 존재 → 의존성 불필요.
- **신규 캠페인/협동전 몸체**(변종·토라스크·감염된 테란·랩터·티라노조르): 멜리에 없음 →
  **블리자드 캠페인/협동전 데이터 모듈을 맵 의존성으로 추가**해 카탈로그를 가져오는 방식 권장.
  **유닛 XML을 맵에 복사하지 말 것.**
- **금지 재확인(CLAUDE.md 불변식)**: 맵 레벨 `RaceData.xml` 추가 금지, 전체 `CRace` 복사 금지,
  보급 상한은 기존 `UnitData.xml`의 부분 `CRace FoodCeiling=800` 오버라이드로만.
  런타임 `c_playerPropSuppliesLimit` 변경 금지.
- **주요 위험**: 캠페인/협동전 의존성을 멜리 맵에 얹으면 카탈로그 충돌로 **시작 유닛 누락/중복**,
  **일꾼 보급 0**, **600 상한** 오버라이드가 깨질 수 있다(프로젝트가 반복적으로 겪은 회귀).
  → **유닛/의존성을 하나 추가할 때마다** `docs/verify/verification-guide.md`의 오프라인 티어 +
  SC2 엔진 테스트로 **정상 시작 유닛과 관측 보급 상한**을 명시 검증하고
  `HANDOFF.md`·`docs/latest_status.md`에 기록.
- **점진적 출시 권장**: (1) 저위험 항목부터 — **토라스크(REPLACE 울트라)** 하나로 파이프라인 검증
  → (2) **변종(ADD)** 배선 추가 → (3) 감염된 테란(수명 속성 편집 필요)·랩터 순.
